# Backend/API Blueprint — Marble Race Web App

## Цілі
- Координувати лобі, ставки та результати гонок без смарт-контракту.
- Забезпечити прозорість (commit–reveal), щоб користувач міг верифікувати симуляцію.
- Інтегрувати платежі TON (та опційно Telegram Stars) через керований гаманець.
- Надавати фронтенду WebSocket/HTTP API з авторизацією через підпис гаманця.

---

## Архітектурні блоки

| Компонент            | Завдання                                                                                           |
|----------------------|-----------------------------------------------------------------------------------------------------|
| Fastify API          | REST/WS маршрути, авторизація, управління лобі, валідація запитів                                   |
| DB (PostgreSQL / SQLite для dev) | Зберігання користувачів, ігор, транзакцій, комісій, рефералів                              |
| TON інтеграція       | Моніторинг вхідних платежів, ініціація виплат, конвертація Stars → TON                              |
| Seed Service         | Генерує seed гонки, публікує hash, логування commit–reveal                                          |
| WebSocket Hub        | Пуш оновлень фронтенду: статус лобі, старт/фініш гонки, reveal, результати                          |

---

## Авторизація
1. Фронтенд викликає `POST /auth/request` → сервер генерує nonce (користувач, IP, TTL) → повертає рядок.
2. Клієнт підписує nonce через TON Connect → `POST /auth/verify` з адресою та підписом.
3. Сервер перевіряє підпис, створює JWT (короткий термін), зберігає сесію.
4. Кожен наступний REST/WS запит містить JWT (Bearer / query param для WS).

## Модель даних (чернетка)

### Users
- `id` (uuid)
- `ton_address`
- `display_name`
- `created_at`
- `referrer_id` (nullable)
- `stats` (JSON: wins, games, volume)

### GameLobby
- `id`
- `status`: `collecting` / `committed` / `running` / `settled` / `cancelled`
- `min_balls`, `max_balls`, `entry_price` (TON, Stars)
- `commit_hash` (SHA256 seed + salt)
- `reveal_seed` (nullable until reveal)
- `created_at`, `start_deadline`, `started_at`, `finished_at`

### Participation
- `id`
- `game_id`
- `user_id`
- `balls` (quantity)
- `payment_tx` (hash, amount, confirmations)
- `stars_invoice_id` (nullable)
- `joined_at`

### TransactionLog
- `id`
- `user_id`
- `game_id`
- `type`: `stake`, `refund`, `payout`
- `amount`
- `tx_hash`
- `status`
- `created_at`

## REST API (v1)

| Метод | URI                         | Призначення                                                                 | Авторизація |
|-------|-----------------------------|------------------------------------------------------------------------------|-------------|
| POST  | `/auth/request`             | Отримати nonce для підпису                                                  | ні          |
| POST  | /auth/verify              | Підтвердити адресу підписом, видати JWT (на dev етапі перевірка спрощена: підпис = nonce) | ні          |
| GET   | `/lobby/current`            | Поточна активна гра, статус збору                                           | опційно     |
| POST  | `/lobby/join`               | Записати намір на участь (баланс, кількість кульок)                          | так         |
| GET   | `/lobby/payment/:id`        | Перевірити статус платежу (polling fallback)                                | так         |
| POST  | `/games/:id/replay`         | Отримати seed, конфіг фізики для повтору гонки (після reveal)               | так         |
| GET   | `/profile/me`               | Баланс, історія ігор, реферальні дані                                       | так         |
| POST  | `/referral/link`            | Генерувати реферальне посилання                                             | так         |

Поточна dev-версія також надає WebSocket `/ws/lobby/state`, який кожні 5 секунд надсилає поточний стан лобі; у майбутньому він транслюватиме реальні події.
Стан лобі повертає поле `track`, де зберігається опис траси (розміри, сегменти Plinko/Funnel/Gate/Rotator/Zigzag, фінішні слоти).

### Track layout (dev)
- width/height — розміри полотна (у пікселях); фронтенд масштабує canvas під контейнер.
- segments — перелік примітивів, що послідовно формують трасу:
  - plinko: сітка штифтів (rows, columns, top, height).
  - funnel: звуження потоку до центрального жолоба.
  - gate: рухома платформа (direction, amplitude, period).
  - rotator: круг з радіусом і швидкістю обертання, додає імпульс кулькам.
  - zigzag: хвилеподібні канали (waves, amplitude).
- slots — кінцева зона фінішу; наразі використовується для відображення базового finish.
### Адмін/внутрішні (JWT з роллю або service token)
- `POST /admin/lobby/new` — створення нового лобі (за розкладом/крон).
- `POST /admin/lobby/cancel` — відміна та запуск рефунда.
- `POST /admin/payments/send` — ручний виклик виплати.
- `POST /admin/seed/reveal` — форсований reveal (на edge-case).

## WebSocket Події

Namespace: /ws/lobby
- lobby_state — повний стан лобі (dev-оновлення кожні 5 секунд).
- commit_announced — сигнал про наявність commit hash (тимчасово генерується локально).
- seed_preview — попередній seed для тестування фізики.
- status_change — оновлення статусу (collecting → commit → ...).

| Подія                 | Payload                                                       |
|-----------------------|---------------------------------------------------------------|
| `lobby_state`         | поточний статус лобі, кількість кульок, залишок часу          |
| `payment_update`      | підтвердження ставки конкретного гравця                       |
| `commit_announced`    | хеш seed + метадані                                            |
| `race_start`          | seed (зашифрований), час старту, список кульок                |
| `race_tick`           | (опційно) елемент реального часу для синхронізації            |
| `race_finish`         | id переможця, статистика                                      |
| `reveal`              | seed + конфіг для валідації                                   |
| `refund_complete`     | статус рефунда для користувача                                |

## Процес гонки (без смарт-контракту)

1. **Collecting**  
   - Користувачі подають `join` → бекенд генерує рахунок: для TON повідомляє адресу/коментар; для Stars — invoice через Bot API.  
   - Система очікує підтвердження транзакції (webhook/poll від TonCenter).

2. **Commit**  
   - Коли мінімум кульок набрано (або дедлайн), бекенд генерує seed: `seed_raw = randomBytes(32)` та `commit_hash = SHA256(seed_raw || lobby_id || timestamp)`.  
   - Всі отримують подію `commit_announced`.

3. **Run**  
   - Через таймер (наприклад, 15 сек) бекенд надсилає `race_start` із зашифрованим seed (наприклад, XOR з ключем, який передається у `reveal`) або просто утримує seed до завершення.  
   - Фронтенд відтворює симуляцію на основі локального генератора псевдовипадковостей (конфіг буде у `reveal`).

4. **Reveal & Settlement**  
   - Після завершення анімації бекенд відправляє `reveal` (seed, timestamp, список кульок у визначеному порядку).  
   - Виконується розрахунок: переможець отримує банк (мінус комісія), інші — нічого.  
   - Бекенд формує транзакції TON (batch або послідовно). Логи — в `TransactionLog`.

5. **Cancel**  
   - Якщо умов нема (замало ставок, таймаут 5 хв), система переводить гру в `cancelled` та повертає кошти.  
   - Перед тим публікує `reveal` пустого seed, щоб не було підозр у маніпуляції.

## TON Платежі

- **Вхідні ставки**:  
  - Користувач отримує address/comment (наприклад, subwallet ID + lobby ID).  
  - Моніторинг через tonapi/toncenter: фільтр по адресі та коментарю.  
  - Щоб уникнути race conditions, кожному payment присвоюємо `payment_id`, перевіряємо amount, confirmations ≥ 1.

- **Виплати**:  
  - Module викликає Toncenter API `sendTransaction` з wallet seed (зберігати у .env/secret store).  
  - На dev — можна використати тестовий гаманець із низькою сумою.  
  - Перед відправкою перевіряємо баланс, ліміти, логування.

- **Telegram Stars (опціонально)**:  
  - Через Bot API `createInvoice` + webhook `successful_payment`.  
  - Внутрішній баланс зберігаємо в БД, при виведенні конвертуємо на TON вручну.

## Безпека та аудит
- Зберігати seed та reveal в audit таблиці (immutable log).
- Підписувати response з seed (наприклад, HMAC) — клієнт може перевірити підпис.
- Логувати всі дії користувачів (IP, user agent) → rate limit.
- Для важливих маршрутів (`/admin/*`) використовувати окремий API-key + 2FA.
- Регулярно створювати snapshots БД і гаманця.
